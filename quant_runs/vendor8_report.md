# Vendor toolchain at 8 seeds: what the full int8 chain costs

Generated by `npu_quant/vendor8_report.py` from the per-run JSONs listed in section 7; no number below is hand-typed.

## 1 What was run

For every seed s = 0..7 and both endpoints of the projection interval (N = 1 = project every step, N = inf = projection off, i.e. snap_every = 0):

1. export of best.pth to a static-shape ONNX graph (input [1,1,3,224,224], output age) - npu_quant/vendor8_prepare.py.
2. FP32 reference on the 200 test bins through onnxruntime (same graph, no quantisation) - npu_quant/vendor8_fp32.py.
3. hb_compile (hbdk4 4.7.5 / hmct 2.6.5, march nash-m) with per-tensor min-max calibration on the same 100 calibration images used for seed 0 - npu_quant/hb_compile_patched.py + npu_quant/hb_config/vendor8_<tag>.yaml.
4. the compiled .hbm run image-by-image on the x86 nash instruction-level simulator (hbrt4-run-model-nash), one process per image, 12-15 workers - npu_quant/vendor8_eval.py.

Both endpoints are the --ema-mode none arm, whose live weights are the deployed ones (scripts/deploy_table.py:451 selects model_state_dict when mode == none); in none the EMA copy never updates (val_mae_ema 0.26-1.16 vs live 0.053-0.076), so exporting the shadow would deploy an untrained initialisation. All runs are ema_decay = 0.99 and split_seed = 0, so all 16 share one validation split, one 100-image calibration set and one 200-image test set.

## 5 What the numbers do and do not support

At this sample size the cost of the full vendor chain is not resolved as strictly positive at both endpoints: at least one 95 % t interval over seeds still contains 0.

At N = 1 the paired delta is +0.002916 [+0.001698, +0.004134] over 8 seeds (8/8 positive, exact two-sided sign test p = 0.007812); at N = inf it is +0.001166 [-0.000400, +0.002732] over 8 seeds (6/8 positive, p = 0.2891).

The two endpoint intervals overlap, so this design does not separate the cost of projecting every step from the cost of not projecting at all; the shared magnitude is the quantity the run-level statement can carry.

This replaces the single-checkpoint readings of the earlier vendor-chain run (npu_quant/out/mae_runtime_relu_qat_s0_N1.json = +0.003834 and npu_quant/out/mae_runtime_relu_qat_s0_Ninf.json = +0.004025, one checkpoint each, and the N = 1 one belongs to the after_snap arm) with a per-seed paired interval at the same endpoints of the projection interval.

What this does not support: (i) the intervals are over the 8 initialisations that completed, all on one fixed split, so they carry no split-to-split variance and cannot be read as a population statement about UTKFace; (ii) the deployed graph is one architecture at every seed, so this is a cost of the toolchain on this model family, not a claim about BPU kernels in general; (iii) the runtime here is the x86 nash instruction-level simulator, so latency, energy and any board-specific scheduling effect remain unmeasured - only numerical behaviour on the deployed graph is observed; (iv) the seeds share one 200-image test set and one 100-image calibration set, so both columns inherit that sampling, and the pairing removes it only from the delta.

Compile median 1576 s (range 1139-2125 s); runtime eval median 1966 s (range 1577-2065 s). Because compile(k+1) overlapped eval(k), one checkpoint costs about 33 min of wall clock when the two stages overlap (59 min if they are serialised), and the runtime eval is the larger half.

Both columns were measured with one or two hbdk4 compiles running next to the eval stream (12-15 workers) on a 16-core box, so they are contended rather than solo timings. The solo seed-0 reference compile recorded in npu_quant/REPORT.md line 113 is 395 s for N = 1, i.e. roughly a quarter of the contended compiles below.

About five to six minutes of one compile are hb_compile's calibration pass: the tool tries batch 8, hits the exported graph's static Reshape to {1, 3, 224, 224}, logs 'Reset batch_size=1 and execute forward again...' and then runs the 100 calibration images one at a time at roughly 2-3 s each. The 16 ONNX exports plus the 16 onnxruntime fp32 baselines took about 7 min of host wall clock in total.
