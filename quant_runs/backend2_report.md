# 第二部署后端：ONNX Runtime 静态 QDQ int8（x86 CPU）

> 本文件由 `scripts/round20_backend2.py` 产出（JSON 原始读数见 `quant_runs/backend2_report.json`，
> 逐图预测见 `quant_runs/backend2_preds/backend2_preds.npz`）。
> 只回答一个问题：**训练侧测到的间隔效应（间隔 1 相对关闭投影 N = ∞ 更差）在 ORT int8 这条独立实现上是否仍然存在、保留多少。**

## 0 一句话结论

**存在，且在一个真正可部署的口径上几乎原样保留**：只量化骨干卷积（`conv` 臂）时，间隔效应在 int8 上是
**+0.020293 [+0.018840, +0.021747]（8/8 同号，精确符号检验 p = 0.0078）**，与 FP32 的
**+0.019531 [+0.017695, +0.021366]** 几乎相同，**保留比例 1.039（逐 seed 均值 1.051，95 % CI [0.926, 1.175]）**；
两个检查点的量化代价差 **+0.000763 [−0.001398, +0.002923]（含 0）**，即**没有检测到"越常投影的检查点越怕量化"**。

全图量化（`full` 臂，ORT 默认口径）在本网络上**不是一个可用后端**：int8 MAE 从 0.0769/0.0574 抬到
0.2174/0.0800，间隔效应被放大到 **+0.137453**（保留比例 7.04），因为**投影过的检查点对量化敏感得多**
（ΔMAE 0.1405 对 0.0226）。这一臂只作**失配诊断**，不进入结论句。


- **ORT 版本：onnxruntime 1.26.0**（providers：`AzureExecutionProvider`、`CPUExecutionProvider`；本报告只用 CPU EP）。
  其余：python 3.13.1、torch 2.12.0+cu132（只用于导出与 torch 侧 FP32）、onnx 1.21.0、numpy 2.4.6。
- 两个臂只差一个参数 `op_types_to_quantize`：
  - `full`（**预注册主口径**，ORT 默认）：`None`，全图所有可量化算子 int8；
  - `conv`（**部署可行口径**）：`["Conv"]`，只量化骨干的 66 个卷积，Transformer 头与逐元素算子保留 fp32。
- 权重量化 per-channel（Conv 沿输出通道轴）、激活 per-tensor；权重量化**对称**、激活量化**非对称**（QInt8）。

## 6 间隔效应穿过本后端保留的比例

定义：**保留比例 = (N1_int8 − Ninf_int8) / (N1_fp32 − Ninf_fp32)**，FP32 侧用同一批 200 张图的 ONNX FP32 读数。

| 臂 | 比值（均值之比） | 逐 seed 比值：均值、95 % CI、范围 |
|---|---|---|
| `conv` | **1.039** | 1.0507，95 % CI [0.9262, 1.1751]，逐 seed 0.854 – 1.344 |
| `full` | 7.038 | 6.9275，95 % CI [4.7979, 9.0571]，逐 seed 4.107 – 11.420 |

即：**部署可行的 `conv` 臂上，间隔效应 100 % 穿过量化（点估计 104 %，区间覆盖 1.0）；全图臂上被放大到 7 倍。**

## 7 为什么有第二个臂：s0 单点诊断（ad-hoc，不进网格）

`full` 臂在 s0（N=1）上 int8 MAE = 0.281464（FP32 0.075129，ΔMAE +0.206335，居中余弦 0.485），
这与本仓库更早的 `quant_runs/H2/quant_result.json`（同一网络、relu_qat、live：cos_centered 0.5291、
MAE_int8_vs_fp32 0.274896）**一致**，所以不是本次脚本的 bug。拆开量化范围后：

| 量化范围（s0, N=1, 同一批 200 张） | int8 MAE | ΔMAE | 居中余弦 |
|---|---|---|---|
| 全图（`full`） | 0.281464 | +0.206335 | 0.4852 |
| 只 Conv（`conv`） | 0.083298 | +0.008169 | 0.9788 |
| 只 MatMul + Gemm | 0.180790 | +0.105661 | 0.5326 |

- 损坏集中在 **MatMul/Gemm**（Transformer 编码器与头），不是卷积骨干。
- 换校准方法无效：Percentile 99.99 → +0.209782、Percentile 99.9 → +0.210551、Entropy → +0.206335（与 MinMax 相同）。
  故**不是校准范围选错**，是 per-tensor int8 激活量化在这个网络上本身不可行。
- 机制线索（读量化图的 Q 尺度）：218 个激活 Q/DQ 中最大的是
  `/temporal/layers.0/self_attn/MatMul_1_output_0`，范围 **±109**（int8 步长 0.854），
  而绝大多数激活的步长在 0.004–0.07 —— 少数量级偏大的张量把 per-tensor 尺度拖坏。
- 因此第二臂取"只量化 Conv"：它保留 int8 的绝大部分计算量（66 个卷积），又是本网络上唯一可用的 int8 口径。

## 8 与厂商 hbdk4 链的关系（不同实现，只能相互印证，不能互相替代）

| | 本报告（ORT） | 厂商链（`npu_quant/out/round20_toolchain.md`） |
|---|---|---|
| 量化器实现 | ORT `quantize_static`（QDQ 图改写，ORT 自带校准流程） | hbdk4 编译链 |
| 权重粒度 | **per-channel** | **per-tensor** |
| 激活 | per-tensor、非对称 QInt8 | per-tensor int8 |
| 校准 | 100 张 `npu_quant/calib`（MinMax） | **同一批** 100 张 |
| 执行 | x86 CPU 上的 ORT CPU EP | nash x86 指令级仿真 |
| 输入 | 同一批 200 张 `npu_quant/testbin` | 同一批 200 张 |

两者是**两条独立实现**：量化粒度（per-channel 对 per-tensor）、图改写方式与执行环境都不同。
它们只能**相互印证**（同一批图、同一批校准、同一个方向），**不能互相替代**——一条链上的读数不能拿来充当另一条链的证据。

印证的落点：厂商链在 **N=20 对 N=∞** 上保留 **95.0 %**（FP32 +0.006828、nash +0.006485，单 run s0）；
本报告在 **N=1 对 N=∞** 上保留 **103.9 %**（n=8 逐 seed 配对）。两条链都指向"间隔带来的训练侧差异在 int8 部署上不会被吃掉"。
注意口径不同：厂商链是单 run、间隔 20；本报告是 8 个 seed、间隔 1。

## 9 延迟（CPU 相对参考，**不是硬件结论**）

单线程、逐图、200 张、同一台机器（`quant_runs/backend2_preds/backend2_latency.json`）：

| 检查点 | FP32 | int8 `full` | int8 `conv` |
|---|---|---|---|
| none_N1 / s0 | 28.5 ms | 43.9 ms | 45.2 ms |
| none_Ninf / s0 | 29.9 ms | 42.8 ms | 42.5 ms |

**int8 在 x86 CPU 上不比 FP32 快**（QDQ 的量化/反量化开销 + CPU EP 没有对应的整数卷积加速路径）。
这只是本机 ORT CPU EP 的相对读数，**不构成任何硬件结论**，也不能用来推断 BPU 上的延迟。

## 10 既有产物的自证、偏离与限制

**自证**：脚本在运行前对 512 个既有文件（`quant_runs/*.{csv,json,md,npz}`、`scripts/*.py`、`npu_quant/*.py`、
`npu_quant/calib/*.npy`、`models/*.py`）各算一次 sha256，运行后再算一次：

```
{"n_frozen_before": 512, "n_frozen_after": 512, "added": [], "removed": [], "changed": ["scripts/round20_backend_ov.py"], "unchanged": 511}
```

- `added` / `removed` 皆空；511 个文件字节级不变。
- **唯一变化项 `scripts/round20_backend_ov.py` 不是本任务的产物**：它是并行进行的 OpenVINO 后端那一路（`backend_ov_*`）
  自己的脚本，本任务从未读写它；本任务名下只新增了 `scripts/round20_backend2.py`、
  `quant_runs/backend2_report.{md,json}`、`quant_runs/backend2_preds/*`、`logs/backend2_*.log`。
- 该条目在 16 个检查点跑完的同一时刻被并行代理改动，属于并发写入，不是本脚本的行为。

**偏离（全部如实记录）**

1. **多了一个臂**：任务只要求一个配置。因为全图量化在本网络上不可用（见 §7），额外加 `conv` 臂；两臂共用同一套
   检查点、同一批图、同一份校准，只差 `op_types_to_quantize`。`full` 仍是预注册主口径，报告与 JSON 都标了 `is_primary`。
2. **网格用 6 进程并行跑**（每进程 4 线程），故 JSON 里的 `latency_ms_*` 是并发下的读数，**不可用**；
   报告 §9 的单线程延迟另有 `--lat` 单独跑，是串行读数。
3. **校准与测试口径与 `scripts/quant_eval.py` 不同**（后者用 val[:200] / val[200:400]）；本任务按用户要求改用
   `npu_quant` 那批（与 nash 同批的 200 张 + 100 张校准），且未修改 `scripts/quant_eval.py`。
4. **"保留比例"用的是均值之比**（分子分母分别是两臂的均值差），逐 seed 比值另列；比值在分母接近 0 时会不稳，
   但本例分母（+0.0195）是 sd 的 9 倍，不存在这个问题。
5. 未做：4 bit / 6 bit 的 ORT 读数（任务只要求 int8）；板端或 GPU 读数（任务禁止）；跨真机加速器验证。
